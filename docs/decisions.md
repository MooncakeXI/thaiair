# บันทึกการตัดสินใจ

## ใช้ src/ layout
ทางเลือกอื่น: flat layout (package อยู่ที่ราก)
เลือกเพราะ: บังคับให้ import จากตัวที่ติดตั้งจริง ไม่ใช่โฟลเดอร์ในเครื่อง
ถ้าลืมใส่ dependency จะพังตั้งแต่บนเครื่องตัวเอง ไม่ใช่ไปพังตอนคนอื่น clone

## repo เดียว (monorepo)
ทางเลือกอื่น: แยก repo api / web
เลือกเพราะ: แยกทีหลังง่าย รวมทีหลังยาก · CI ชุดเดียว · คนดู portfolio เปิดลิงก์เดียว

## dependencies = [] ตั้งต้น
ทางเลือกอื่น: ใส่ pandas/sklearn/fastapi ไว้ล่วงหน้า
เลือกเพราะ: ใส่เมื่อมีบรรทัด import จริงเท่านั้น — dependency ที่ไม่ได้ใช้
ทำให้ install ช้า image อ้วน และหกเดือนหลังไม่มีใครกล้าลบ

## แยก [dev]
ทางเลือกอื่น: รวมทุกอย่างใน dependencies
เลือกเพราะ: Docker image ตอนเสิร์ฟไม่ควรมี pytest — ใหญ่ขึ้นเปล่าๆ และเพิ่มของที่ต้องแพตช์

## เวอร์ชันอยู่ที่ __init__.py ที่เดียว (dynamic)
ทางเลือกอื่น: เขียนใน pyproject.toml
เลือกเพราะ: สองที่จะไม่ตรงกันสักวัน แล้วไม่มีใครรู้ว่าอันไหนจริง

## เก็บข้อมูลดิบเป็นแนวยาว (long) ไม่ใช่แนวกว้าง
ทางเลือกอื่น: หนึ่งคอลัมน์ต่อหนึ่งพารามิเตอร์
เลือกเพราะ: แหล่งข้อมูลแต่ละเจ้าส่งรูปไม่เหมือนกันอยู่แล้ว (OpenAQ เอียง long,
Open-Meteo เป็น wide) เราต้องเลือกรูปของเราเองไม่ว่ายังไง — เลือก long
เพราะเพิ่มพารามิเตอร์ใหม่ไม่ต้องแตะสัญญาเลย
และถอยง่ายกว่า: long → wide คือ pivot บรรทัดเดียว แต่ wide → long ต้องรื้อสัญญาใหม่หมด

## timestamp เก็บเป็น UTC แบบไม่มี tz ติด (naive)
ทางเลือกอื่น: tz-aware UTC / tz-aware เวลาไทย
เลือกเพราะ: parquet กับ CSV เขียนอ่านเหมือนกัน ไม่มี dtype แปลก · ไม่มีการแปลงซ้อน
· ไทยไม่มี DST ทำให้ +7 คงที่ตลอดกาล การแปลงตอนแสดงผลจึงไม่กำกวม
⚠️ ผลที่ตามมา: แหล่งที่คืนเวลาไทยแบบไม่มี tz (Air4Thai) ต้องแปลงก่อนเรียก conform()
ไม่งั้นข้อมูลเลื่อน 7 ชม. โดยไม่มีอะไรฟ้อง

## parquet ไม่ใช่ CSV
เลือกเพราะ: CSV ทำ dtype หาย (เวลากลายเป็นสตริง, station_id กลายเป็นตัวเลข)
ซึ่งเป็นต้นตอบั๊กที่ตามยาก · ไฟล์เล็กกว่า 5–10 เท่า

## ไม่มีคอลัมน์ "unit"
เลือกเพราะ: บังคับหน่วยมาตรฐานต่อพารามิเตอร์ที่ชั้นแหล่งข้อมูลแทน
ถ้ามีคอลัมน์หน่วย วันหนึ่งจะมีแถวที่หน่วยไม่ตรงปนเข้ามาโดยไม่มีใครรู้ตัว

## เก็บแถวที่ value เป็น NaN ไว้ (ไม่ทิ้ง)
เลือกเพราะ: "วัดแล้วไม่ได้ค่า" เป็นข้อมูลคนละอย่างกับ "ไม่ได้วัด"
และโมเดลควรได้เห็นความต่างนั้น

## ทำแหล่งสังเคราะห์ก่อนต่อ API จริง
เลือกเพราะ: เขียนชั้นบนได้ทันทีโดยไม่ติดหล่ม API key · CI รันได้โดยไม่ต้องมี secret
· สร้างเคสยาก (ค่าหาย) ได้ตามใจ

## ใช้ Protocol ไม่ใช่ ABC สำหรับสัญญาแหล่งข้อมูล
ทางเลือกอื่น: abstract base class
เลือกเพราะ: แหล่งข้อมูลเราเป็นฟังก์ชัน ไม่ใช่อ็อบเจกต์ที่มีสถานะหรือวงจรชีวิต
Protocol ยังทำให้แหล่งที่ไม่ได้ import อะไรของเราเลยเสียบเข้าได้
⚠️ Protocol ไม่บังคับอะไรตอนรัน ตัวบังคับจริงคือเทสต์ — จะกลายเป็นตัวบังคับเมื่อใส่ mypy

## ทะเบียนแหล่งข้อมูลอยู่ใน sources/__init__.py ไม่ใช่ใน CLI
เลือกเพราะ: ทะเบียนเป็นเรื่องของชั้นข้อมูล เทสต์ไม่ควรต้อง import CLI เพื่อดูทะเบียน

## เทสต์ parametrize จากทะเบียน + มีเทสต์ตรวจว่าทุกโมดูลลงทะเบียนครบ
เลือกเพราะ: แหล่งใหม่ถูกเทสต์อัตโนมัติโดยไม่ต้องมีใครจำได้ว่าต้องเขียนเทสต์
และถ้าลืมลงทะเบียน เทสต์ทะเบียนจะจับ — สองด่าน ไม่มีทางหลุดทั้งคู่

## ทำ long → wide ด้วย .pivot() ไม่ใช่ .pivot_table()
เลือกเพราะ: pivot โยน error เมื่อเจอคีย์ซ้ำ ส่วน pivot_table เฉลี่ยให้เงียบๆ
ซึ่งจะกลบบั๊กข้อมูลซ้ำที่เราเขียนเทสต์ดักไว้ตั้งแต่ขั้น 2

## กรอบของปัญหา: ฟีเจอร์ที่แถว t ใช้ข้อมูลถึง t ได้ · เป้าหมายคือ t + horizon
ผลที่ตามมา: rolling ที่รวมค่า ณ t เข้าไปด้วย "ถูกต้อง" ไม่ใช่ leakage
เพราะตอนพยากรณ์เรารู้ค่าปัจจุบันอยู่แล้ว
horizon เป็นพารามิเตอร์ โดยคำสั่งเทรนใช้ค่าเริ่มต้น 24 ชั่วโมง

## groupby station_id ก่อน shift/rolling ทุกครั้ง + sort ก่อน groupby
เลือกเพราะ: shift/rolling ทำงานตามลำดับแถว ไม่ได้อ่าน timestamp
ถ้าลืม ค่าของสถานีหนึ่งจะไหลข้ามไปเป็นฟีเจอร์ของอีกสถานีตรงรอยต่อ โดยไม่มี error

## min_periods = 75% ของหน้าต่าง ไม่ใช่ 100%
ทางเลือกอื่น: เรียกร้องหน้าต่างเต็ม
เลือกเพราะ: ข้อมูลจริงมีรูเสมอ · ค่าหาย 3% ทำให้หน้าต่าง 24 ชม. โดน 1−0.97²⁴ ≈ 52%
วัดจริงแล้วเสียข้อมูลไป 2,134/4,320 แถว → ลดเป็น 51 แถวหลังแก้
ยอมให้ฟีเจอร์คลาดเคลื่อนเล็กน้อย ดีกว่าให้โมเดลเห็นตัวอย่างน้อยลงครึ่งหนึ่ง

## เข้ารหัสเวลาแบบวงกลม (sin/cos) ด้วยชั่วโมงเวลาไทย
เลือกเพราะ: ชั่วโมง 23 กับ 0 ติดกันจริงแต่ห่างกัน 23 หน่วยถ้าใส่เป็นเลขดิบ
ใช้เวลาไทยเพราะรูปแบบรถติดเป็นเรื่องของเวลาท้องถิ่น ไม่ใช่ UTC

## ย้าย BANGKOK_UTC_OFFSET ไปไว้ที่ schema.py
เลือกเพราะ: ค่าคงที่ที่ถูกใช้สองที่ควรมีที่มาที่เดียว — มันเป็นส่วนหนึ่งของข้อตกลงเรื่องเวลา

## baseline คือ persistence ("ชั่วโมงหน้า = ชั่วโมงนี้")
เลือกเพราะ: ตัวเลข MAE ตัวเดียวไม่มีความหมายถ้าไม่มีของเทียบ
และ persistence เป็น baseline ที่โหดที่สุดสำหรับข้อมูลรายชั่วโมง

## แบ่ง train/test ตามเวลา ไม่ใช่สุ่ม
เลือกเพราะ: การสุ่มทำให้โมเดลเห็นอนาคตตอนเทรน ซึ่งตอน deploy มันไม่มีทางเห็น
จุดตัดคำนวณจาก "เวลาที่ไม่ซ้ำ" ไม่ใช่จำนวนแถว เพราะหนึ่งเวลามีหลายสถานี

## ใช้ MAE เป็นหลัก RMSE เป็นตัวรอง ไม่ใช้ MAPE
เลือกเพราะ: MAPE หารด้วยค่าจริง และ PM2.5 หน้าฝนลงไปแตะ 2 µg/m³
พลาด 2 หน่วยตรงนั้นกลายเป็น 100% error ทั้งที่ไม่มีนัยสำคัญ

## ใช้ HistGradientBoostingRegressor
เลือกเพราะ: รับ NaN ได้เองโดยไม่ต้อง impute — ฟีเจอร์ lag/rolling ของเรามี NaN เยอะ
การ impute เป็นการตัดสินใจเพิ่มอีกชั้นที่อาจผิดโดยไม่รู้ตัว

## ⚠️ หนี้ที่รู้ตัว: แบ่งครั้งเดียวทำให้ทดสอบแค่ฤดูเดียว
ชุดทดสอบปัจจุบันคือ พ.ค.–ก.ค. (หน้าฝน) — ไม่ได้วัดหน้าเผาเลย
ซึ่งเป็นช่วงที่แอปมีประโยชน์ที่สุด → ต้องทำ walk-forward validation

## ⚠️ หนี้ที่รู้ตัว: โมเดลไม่ดีกว่า baseline ในหน้าเผา
วัดเมื่อ 29 ส.ค. ด้วยข้อมูลสังเคราะห์ 1 ปี (--test-fraction 0.45)
  หน้าฝน   baseline 7.575  model 6.702  +11.5%
  หน้าเผา  baseline 10.117 model 10.071  +0.5%   ← ตัน

สาเหตุที่น่าจะเป็น: synthetic.py ให้ลมเป็นค่าสุ่มอิสระรายชั่วโมง ซึ่งทำนายไม่ได้เลย
หน้าฝนค่าต่ำจนโดน clip ที่ 2.0 บ่อย ความสุ่มเลยถูกตัดออกไปเยอะ ทำให้ดูเหมือนโมเดลเก่ง

→ ยังไม่จูนโมเดล เพราะจูนบนข้อมูลปลอมคือปรับให้เก่งในโลกที่ไม่มีอยู่
→ ต้องต่อข้อมูลวัดจริงก่อน (OpenAQ/Air4Thai) ถึงจะรู้ว่าปัญหานี้จริงหรือไม่

## รายงานผลแบบซอยตามฤดู (ไม่ใช่แบ่งข้อมูลเทรน)
แบ่งเพื่อเทรน = ให้โมเดลเห็นข้อมูลน้อยลง (ตัดเทรน 31% ทำให้แย่ลง 46% — วัดมาแล้ว)
แบ่งเพื่อรายงาน = ให้เราเห็นความจริงมากขึ้น
ฤดูใส่เป็นฟีเจอร์ผ่าน doy_sin/doy_cos อยู่แล้ว โมเดลแตกกิ่งตามฤดูเองได้
นี่คือรากฐานของ sliced monitoring ในขั้น 9

## artifact เก็บมากกว่าตัวโมเดล
เก็บ feature_columns + horizon + trained_at + train_range + metrics
เลือกเพราะ: โมเดลเปล่าคือกล่องปริศนา — สามเดือนหลังตอบไม่ได้ว่ามันคาดหวังอะไร
feature_columns คือตัวที่กัน train/serve skew โดยตรง (API เลือกและเรียงคอลัมน์ตามนี้)
ตรวจคีย์ครบทั้งตอนบันทึกและตอนโหลด — artifact เก่าจะพังตอนสตาร์ต ไม่ใช่ตอนรับ request แรก

## บันทึกโมเดลหลังผ่านเกณฑ์ baseline เท่านั้น
sys.exit(1) อยู่ก่อนบรรทัดบันทึก → โมเดลที่แพ้ baseline ทับตัวเก่าไม่ได้
นี่คือ guardrail ตัวแรกของโปรเจกต์ (เวอร์ชันย่อของ "ห้ามเลื่อนขึ้น Production ถ้าแย่กว่าเดิม")

## /health กับ /ready แยกกัน และโหลดโมเดลไม่สำเร็จไม่ทำให้ process ตาย
/health = "ต้อง restart ไหม" · /ready = "ส่ง traffic มาได้ไหม"
ถ้ารวมเป็นอันเดียว pod ที่โมเดลยังโหลดไม่เสร็จจะโดน restart วนไม่จบ

## อ่าน config จาก env ตอนใช้ ไม่ใช่ตอน import
เลือกเพราะ: อ่านตอน import = ตรึงค่าตลอดอายุ process → เทสต์ชี้ไปที่ข้อมูลทดสอบไม่ได้
(เทสต์เป็นตัวบังคับให้เจอ — เป็นครั้งที่ 3 ที่เทสต์ขับการออกแบบ)

## ⚠️ หนี้: API ตอบตัวเลขแม้ฟีเจอร์เป็น NaN เกือบหมด
ยืนยันแล้วด้วยมือ — แถวแรกของชุดข้อมูลตอบ 7.28 โดยไม่มีคำเตือน
ต้องมีตัวบอกความมั่นใจ หรือปฏิเสธเมื่อฟีเจอร์ขาดเกินเกณฑ์ → ทำพร้อมขั้น 9

## ⚠️ หนี้: API โหลดประวัติตอนสตาร์ตแล้วไม่รีเฟรช
ข้อมูลใหม่ต้อง restart — นี่คือปัญหาที่ feature store กับ orchestration เกิดมาเพื่อแก้

## Deploy บน Render Free ด้วย snapshot คงที่
ทางเลือกอื่น: AWS ECS, scheduler ดึงข้อมูลรายวัน, database
เลือกเพราะ: portfolio ต้องมี public API โดยไม่เสียค่า hosting
image พกเฉพาะ model และ observations snapshot ที่ใช้เสิร์ฟ จึงไม่ต้อง database
หรือ OpenAQ API key บน Render · ยอมรับ cold start และอัปเดต snapshot ด้วยมือ
