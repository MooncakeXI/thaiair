# บันทึกการตัดสินใจ

## ใช้ src/ layout
ทางเลือกอื่น: flat layout (package อยู่ที่ราก)
เลือกเพราะ: บังคับให้ import จากตัวที่ติดตั้งจริง ไม่ใช่โฟลเดอร์ในเครื่อง
ถ้าลืมใส่ dependency จะพังตั้งแต่บนเครื่องตัวเอง ไม่ใช่ไปพังตอนคนอื่น clone

## repo เดียว (monorepo)
ทางเลือกอื่น: แยก repo api / web
เลือกเพราะ: แยกทีหลังง่าย รวมทีหลังยาก · CI ชุดเดียว · คนดู portfolio เปิดลิงก์เดียว

## dependencies = [] ตั้งต้น
ทางเลือกอื่น: ใส่ pandas/sklearn/fastapi ไว้ล่วงหน้า
เลือกเพราะ: ใส่เมื่อมีบรรทัด import จริงเท่านั้น — dependency ที่ไม่ได้ใช้
ทำให้ install ช้า image อ้วน และหกเดือนหลังไม่มีใครกล้าลบ

## แยก [dev]
ทางเลือกอื่น: รวมทุกอย่างใน dependencies
เลือกเพราะ: Docker image ตอนเสิร์ฟไม่ควรมี pytest — ใหญ่ขึ้นเปล่าๆ และเพิ่มของที่ต้องแพตช์

## เวอร์ชันอยู่ที่ __init__.py ที่เดียว (dynamic)
ทางเลือกอื่น: เขียนใน pyproject.toml
เลือกเพราะ: สองที่จะไม่ตรงกันสักวัน แล้วไม่มีใครรู้ว่าอันไหนจริง

## เก็บข้อมูลดิบเป็นแนวยาว (long) ไม่ใช่แนวกว้าง
ทางเลือกอื่น: หนึ่งคอลัมน์ต่อหนึ่งพารามิเตอร์
เลือกเพราะ: แหล่งข้อมูลแต่ละเจ้าส่งรูปไม่เหมือนกันอยู่แล้ว (OpenAQ เอียง long,
Open-Meteo เป็น wide) เราต้องเลือกรูปของเราเองไม่ว่ายังไง — เลือก long
เพราะเพิ่มพารามิเตอร์ใหม่ไม่ต้องแตะสัญญาเลย
และถอยง่ายกว่า: long → wide คือ pivot บรรทัดเดียว แต่ wide → long ต้องรื้อสัญญาใหม่หมด

## timestamp เก็บเป็น UTC แบบไม่มี tz ติด (naive)
ทางเลือกอื่น: tz-aware UTC / tz-aware เวลาไทย
เลือกเพราะ: parquet กับ CSV เขียนอ่านเหมือนกัน ไม่มี dtype แปลก · ไม่มีการแปลงซ้อน
· ไทยไม่มี DST ทำให้ +7 คงที่ตลอดกาล การแปลงตอนแสดงผลจึงไม่กำกวม
⚠️ ผลที่ตามมา: แหล่งที่คืนเวลาไทยแบบไม่มี tz (Air4Thai) ต้องแปลงก่อนเรียก conform()
ไม่งั้นข้อมูลเลื่อน 7 ชม. โดยไม่มีอะไรฟ้อง

## parquet ไม่ใช่ CSV
เลือกเพราะ: CSV ทำ dtype หาย (เวลากลายเป็นสตริง, station_id กลายเป็นตัวเลข)
ซึ่งเป็นต้นตอบั๊กที่ตามยาก · ไฟล์เล็กกว่า 5–10 เท่า

## ไม่มีคอลัมน์ "unit"
เลือกเพราะ: บังคับหน่วยมาตรฐานต่อพารามิเตอร์ที่ชั้นแหล่งข้อมูลแทน
ถ้ามีคอลัมน์หน่วย วันหนึ่งจะมีแถวที่หน่วยไม่ตรงปนเข้ามาโดยไม่มีใครรู้ตัว

## เก็บแถวที่ value เป็น NaN ไว้ (ไม่ทิ้ง)
เลือกเพราะ: "วัดแล้วไม่ได้ค่า" เป็นข้อมูลคนละอย่างกับ "ไม่ได้วัด"
และโมเดลควรได้เห็นความต่างนั้น

## ทำแหล่งสังเคราะห์ก่อนต่อ API จริง
เลือกเพราะ: เขียนชั้นบนได้ทันทีโดยไม่ติดหล่ม API key · CI รันได้โดยไม่ต้องมี secret
· สร้างเคสยาก (ค่าหาย) ได้ตามใจ

## ใช้ Protocol ไม่ใช่ ABC สำหรับสัญญาแหล่งข้อมูล
ทางเลือกอื่น: abstract base class
เลือกเพราะ: แหล่งข้อมูลเราเป็นฟังก์ชัน ไม่ใช่อ็อบเจกต์ที่มีสถานะหรือวงจรชีวิต
Protocol ยังทำให้แหล่งที่ไม่ได้ import อะไรของเราเลยเสียบเข้าได้
⚠️ Protocol ไม่บังคับอะไรตอนรัน ตัวบังคับจริงคือเทสต์ — จะกลายเป็นตัวบังคับเมื่อใส่ mypy

## ทะเบียนแหล่งข้อมูลอยู่ใน sources/__init__.py ไม่ใช่ใน CLI
เลือกเพราะ: ทะเบียนเป็นเรื่องของชั้นข้อมูล เทสต์ไม่ควรต้อง import CLI เพื่อดูทะเบียน

## เทสต์ parametrize จากทะเบียน + มีเทสต์ตรวจว่าทุกโมดูลลงทะเบียนครบ
เลือกเพราะ: แหล่งใหม่ถูกเทสต์อัตโนมัติโดยไม่ต้องมีใครจำได้ว่าต้องเขียนเทสต์
และถ้าลืมลงทะเบียน เทสต์ทะเบียนจะจับ — สองด่าน ไม่มีทางหลุดทั้งคู่
